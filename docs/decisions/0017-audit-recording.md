# ADR-0017: Audit recording inside the business transaction

- **Status:** Accepted
- **Date:** 2026-10-03

## Context
ADR-0012 defines what the audit log contains and who may read it. This record covers how events are written, so that the trail is complete, trustworthy and free of personal data. The audit infrastructure is built before the features that need it, so every later feature records its events from the start instead of being retrofitted.

## Decision
- Events are recorded through one `AuditService.record(...)` method that requires an **existing transaction** (`Propagation.MANDATORY`). The audit row and the business change commit or roll back together, and calling it outside a transaction fails immediately.
- The event type determines an **allow-list of metadata keys** (for example `ORGANIZATION_CREATED` allows `name` and `slug`). Unknown keys, null values and values longer than 500 characters are rejected as programming errors, so a developer cannot quietly start logging emails, tokens or free text.
- Metadata is stored as `jsonb` and built by PostgreSQL (`jsonb_build_object` with bound parameters). No JSON text is assembled in Java, so there is no escaping to get wrong.
- `audit_logs` is **append-only at the database level**: triggers reject `UPDATE`, `DELETE` and `TRUNCATE`.
- The table has no foreign keys, so history survives what it describes. `event_type` and `target_type` have no CHECK constraint, because values are validated in code and every new event type would otherwise need a migration; the table is history and must never be made unwritable by a schema change.
- Identifiers are time-ordered UUIDs (version 7) generated by the application, which keeps the index append-friendly.
- Failed or rejected operations are not audited. Abuse and failed logins are handled by rate limiting and logs, not by the audit trail.
- Viewing is limited to Owners and Admins of the organization (platform administrators see only platform-scoped events), as in ADR-0012. The view endpoint arrives with organizations.

## Alternatives considered
- **Writing audit rows after the transaction commits (events):** a crash between commit and audit would lose the record. Rejected for sensitive operations.
- **Database triggers on business tables:** capture changes without business meaning (who and why).
- **Hibernate Envers:** versioned snapshots of entities, not business events with a defined schema and allow-list.

## Consequences
- The triggers protect against application bugs and SQL injection through the application, not against a database owner or superuser who can drop them. Real separation needs a restricted runtime database role (no ownership of the table) distinct from the migration role. That is a deployment task (Phase 9). The local Docker database user is a superuser, so locally the triggers are the only guard.
- Retention and archival must be a deliberate, separate process; it cannot use ordinary `DELETE`.
- The audit service is called from many modules. It is a small, stable API, and events from different modules share one table.
